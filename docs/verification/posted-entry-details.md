# 正式账目明细追问与草稿意图分流

2026-10-19。复现使用者先问“看一下我今天花了多少钱”，再问“具体的账目给我看一下”，却收到“本会话没有待确认草稿”。

## 已确认原因与版本边界

旧版在微信入口先运行草稿意图分类器，只给分类器当前文字和草稿状态，没有上一条正式查询的条件。真实模型通过完整 WechatBot 收件、分类、会话及发送流程复现：第二条消息只增加分类调用，未进入正式查账会话，直接返回没有草稿。此外，原查询协议仅有汇总、分组和趋势，没有逐笔明细结果。

先前验证直接调用微信专用 Conversation 接口，绕过了 WechatBot 入口的分类和发送处理，因此不能证明这条流程通过。本轮保留这一覆盖缺口，不用后面的查询成功代替入口验证。

## 最小修复

- 普通会话和微信的共同分类器接收当前会话的上一条权威查询条件；明确区分正式账目明细、待确认草稿和入账同意。查看明细属于只读查询，不赋予确认权限。
- `query_ledger` 新增 `entries` 视图及分页，沿用原日期、币种、类目、标签和关键词，直接复用受保护账目查询。每页 5 笔，包含名称、日期、类型、原币与折合金额、分类、标签及独立备注；退款使用自身备注和发生日期。
- 只在明确请求明细时读取逐笔内容；普通汇总不把逐笔备注发送给模型。模型的金额仍使用明确币种的主单位字符串，业务记录及原工具历史保持最小单位整数。
- 备注在聊天中最多显示 200 个 Unicode 码点，并标记节选；完整备注在账目和备份中保留。微信逐笔渲染 Markdown，长消息整条保留可见条目并明确说明仅显示部分，不截断一条后静默跳到下一页。网页与手机聊天卡片也展示同一份明细。
- 后续查询重新读取当前记录，条件变化重置页码，入账后的同轮报表刷新同步刷新明细。账目查询与报表版本不一致时拒绝混合结果。

## 本轮证据

受保护接口的明细及分页回归、完整 WechatBot 分类至发送回归、金额与 Markdown 格式回归通过；手机／PC 相关 14 项浏览器用例通过，包含刷新恢复及已有确认流程。真实模型完整入口回归通过：5 次意图分类、10 次主模型请求，15 次真实请求均 HTTP 200，覆盖正式明细、明确查看空草稿、存在待确认草稿时仍只显示已入账记录；微信传输为替身，D1／DO 为临时隔离实例。

最终 `pnpm check` 通过：52 项单元测试、413 项 Workers 测试，另 1 项既有可选 SDK 活动测试跳过；551 项中英翻译键一致，格式、类型检查通过。`pnpm build` 与 `pnpm check:private` 通过。代码提交 `b4dee98` 的[完整 CI](https://github.com/ISheepp/Moni/actions/runs/39250130464)通过，包含 74 项浏览器测试。

该代码已发布至现有专用部署，云端构建成功。在独立网页测试会话中，以真实模型依次提交“看一下我今天花了多少钱”和原句“具体的账目给我看一下”；请求明确携带 `review: null`，经过普通会话与微信共用的意图分类，未绕过入口。线上返回 `entries` 视图，保留上一条查询条件，卡片展示真实查询得到的逐笔金额、分类和备注，逐项与受保护账目接口核对一致。首次明细请求在 55 秒时被测试工具取消，服务端记录为已中断；核对状态后使用页面既有重试功能，最终运行完成且只保留一条原始用户消息。未修改线上等待或重试策略。

线上账目总数、金额合计、完整记录及入账权限模式与验证前一致。仅新增独立测试会话历史，没有新建消费、执行确认或退款。本轮未向个人微信发送新的测试消息；真实模型的完整 WechatBot 入口测试使用合成传输，线上验证证明共用分类及实际账目明细正常，不能代替腾讯真实收发与手机渲染验收。
