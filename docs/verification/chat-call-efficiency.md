# 记账调用链与历史工具结果的精简

2026-10-20，基于 `8eccb89` 的优化；本地验证及授权后的发布复验分别记录如下。

## 已确认的成本来源

线上小费收入所在会话的权威历史显示，主模型依次调用 `get_ledger_context`、`prepare_draft`，然后再生成回复。此前系统提示要求先读取账本上下文，导致主币种、日期、类目等应用已经能直接读取的资料，也要占一次模型往返。确认意图识别还会独立调用模型；不把截图中的每条 API 请求当成一次正式入账。

长会话此前把旧工具结果中的完整 JSON 一并交给摘要模型。旧查询明细和草稿快照会被分批处理，增加串行请求。隔离的真实 D1／DO 用例中，一条合成小费收入触发 6 次请求，其中 3 次为历史摘要；该请求数断言已在修复前实际失败。

## 最小改动

- 将已有账本上下文读取逻辑复用为 `readContext`，在主模型开始前提供当前资料，普通会话与微信共同使用。模型仍可按需调用同一工具刷新；日期、金额、类目、草稿版本和入账权限校验不变。
- 继续使用 TanStack AI 官方 `withCompaction` 和 `composeStrategies`。超过上下文预算时，先把本轮之前的工具结果替换成短标记；保留工具调用配对、使用者消息以及本轮全部工具结果。精简后仍超出预算，才执行既有摘要和滑动窗口。
- 只改变提供给模型的投影与检查点，不删除 D1 中的原始消息。摘要、恢复及完整历史分页仍可使用原始记录。统计必须重新查账，确认必须读取权威草稿；旧工具结果与摘要均不获得入账权限。
- 超大的可选初始上下文继续允许问候等不依赖该资料的请求；其他读取错误会取消并清理本轮，不能跳过执行权限校验。

没有压缩主模型循环次数上限，也没有增加写操作自动重试。复杂查询、需要补充信息或服务失败时仍可能超过三次请求。

## 本地验证

- 同一合成场景从 6 次请求降至 3 次，历史摘要从 3 次降至 0 次；首次主模型请求已有账本资料，原始历史保持一致。
- 微信完整接收流程同样为 1 次意图识别、2 次主模型请求；确认前没有正式账目，自然语言确认后只有 1 笔收入，重复投递确认仍为 1 笔。另验证超大待确认草稿不会阻断普通回复。
- 完整 `pnpm check` 通过：59 项单元、420 项 Workers 测试，1 项既有可选测试跳过；561 个中英键、Biome 和类型检查通过。
- 最终生产构建通过一次；私密配置扫描与 Git 空白检查通过。
- 手机／PC 完整浏览器检查为 78 项通过、2 项 AI 设置用例失败。失败原因是导航过程中通用 textbox 选择器匹配到了旧设置表单，改为等待聊天输入框的明确可访问名称后，两项定向复测通过；没有为此修改产品界面或重复构建。

## 真实服务与上线边界

本机私密配置与上一轮已核对的线上配置不同。使用真实 `gpt-6-luna` 和 Responses 对合成账目进行隔离联调：旧版遇到摘要期限并最终中止；优化后已观察到不再请求历史摘要，但完整流程出现分类超时或续轮 HTTP 400。仅运行主模型工具链也收到同样的 400，供应商报错为会话上下文与可用资源不兼容；尚未将该报错归因为本次优化或特定供应商内部原因。

这些失败均不记为真实联调通过，也不能用于宣称线上耗时已降低。没有切换产品模型、协议或供应商，没有关闭确认校验来通过测试。真实凭据只从被忽略的本机配置读取，日志及合成诊断请求保存在被忽略的私密目录中；没有向真实微信发送测试消息或修改线上账目。

这些真实结果证明当前线上供应商能够正常识别、查账并连续追问，且已不再多读一次账本上下文。两轮都没有长历史，不把它们当作线上历史摘要优化的对照实验；合成收入的 6→3 请求以及自然确认、重复确认验证仍来自隔离真实 D1／DO 的可控服务用例。线上端到端耗时有明显波动，本轮没有同一线上场景的优化前耗时基线，尚不能宣称响应时间已稳定达标。
