# 微信待入账提醒与批量确认

2026-10-19。使用者确认先交付文字统计，并要求未入账草稿有提醒、可以批量确认。本轮不实现图片图表，不改变本人确认／直接入账的权限选择。

## 已确认的问题与复现

1. 创建一份未入账草稿，再查询统计。原微信回复只有正式账目查询结果，缺少未入账提醒。通过受保护接口、本地真实 D1/DO 的定向测试先复现失败，加入程序生成的提醒后通过。
2. 连续创建两份草稿，再说“把没入账的都记上”。原确认分类只有单份确认，不能表达批量请求；原回复只保留最近工具草稿的格式化内容，不保留模型自由正文中的旧草稿提醒。新增测试先得到“暂时没能判断你的意思”，补齐批量核对与入账后通过。

根因分别位于微信回复组装与确认引用的范围。不是通过把所有同意词硬编码为入账来修复；仍由独立 TanStack AI 工具分类实际本人消息，程序执行账务检查。

## 修复后的外部行为

- 普通新草稿、查账和入账回执有遗漏待确认内容时，展示本会话草稿份数、账目笔数，并说明尚未入账、不计统计。完整展示中的草稿不重复催促；明确暂不入账时保留草稿而不立即追问。不新增定时提醒。
- 自然语言请求一起核对时列出所有完整草稿；明确要求全部入账但尚未完整核对时，也先展示明细，等待下一条同意。普通确认只绑定最近展示的一份或一批，不包含其他会话或随后新增的草稿。
- 一批最多 20 笔且必须能完整展示。备注、日期、类目、标签、原币与固定折算依据沿用单份排版。信息不全明确排除，超长则到网页核对；同日、同币种、同金额提示可能重复，不自动合并或删除。
- “全部确认”可确认已完整列出的一批，已告知排除且仍缺信息的草稿继续保留，不导致重复核对循环。排除 ID 随展示引用记录；该草稿后来变完整时重新展示，不能沿用此前的批准。
- 每份 ID／版本写入同一个展示引用，微信发送成功后启用。接收消息时绑定当时引用，提前排队的同意不能批准后来展示的批次；持久化兼容旧版单份引用。
- 单份及批量共用金额、换算和账目写入检查。批量账目、草稿状态和回执由同一 D1 事务提交，失败整批回滚；保留活动数据集、恢复锁、渠道撤销及幂等保护。
- 修改、取消、目标缺失、网页抢先确认都要求重新核对剩余目标。明确“全部”时重新读取待确认集合，且在提交事务内检查没有新增的范围外待确认草稿。重复确认、回复重试和进程恢复不重复记账。

## 本轮验证

| 层次 | 结果 |
| --- | --- |
| 微信集成 | 最终全量运行中的 68 项微信测试通过。模型和微信使用可控替身；账本与会话使用真实本地 D1/DO，并经受保护接口核对。 |
| 批量新增回归 | 提醒、自然批量核对、只确认最新后提醒旧草稿、不完整排除、疑似重复、超长拒绝、修改竞态、网页确认竞态、取消、整批写失败回滚、回执重试、新草稿加入期间的两种确认范围、提前排队的确认、否定／修改／部分同意。 |
| 单元 | 18 项通过，包含保留完整统计条目与为提醒预留回复预算。 |
| 真实模型 | 指定私密配置下的 57 组合成自然语言分类全部通过。只请求模型，不读写账本，不发送微信；不将其当作真实账号端到端入账验收。 |
| 翻译与类型 | 517 个中英文键一致，翻译已编译；类型检查通过。 |
| 全量检查 | `pnpm check` 最终通过：169 个文件格式检查、18 项单元、245 项 Worker 通过且 1 项原有跳过、类型检查通过。 |
| 构建 | `pnpm build` 通过。 |
| 私密配置 | 构建后 `pnpm check:private` 通过；公开源码、资源和构建产物未发现本机私密配置值。 |

首次全量回归与构建并行时，既有的“版本变更后重新核对”测试触发 5 秒超时，其余 243 项 Worker 通过；停止并行构建后，独立重跑全量 244 项通过，未增大测试超时或修改该测试。随后补充“已排除草稿后来变完整”及避免重复核对循环的回归，最终全量 245 项通过。执行结果分别记录，不将首次失败隐藏为成功。未执行提交、推送或云端部署。

最终构建已用于重启本机隔离持久化服务。受保护状态接口确认微信已连接、权限仍为“由我确认”；中文页面及引用的 5 个脚本／样式资源均返回 200。该检查没有发送真实账目或确认真实草稿，不等同于手机批量入账验收。

- `MONI_REAL_WECHAT_INTENT_SMOKE=1 pnpm exec tsx scripts/real-wechat-intent-smoke.ts`

手机上的真实批量核对／确认仍待本人实际使用验证；没有代替本人批准任何真实草稿，也未删除或合并疑似重复记录。已有旧会话的上下文长度上限保持原规格，普通 AI 记账／查询超限仍需本人新建会话，旧历史和账目保留；本轮不自动清空上下文。
