# 微信会话场景回归

2026-10-19。使用者要求直接在项目内测试微信会话，扩大覆盖正常操作、边缘情况和故障。测试使用独立合成账本；不操作桌面微信，不向个人账本注入测试数据，不为测试开放正式接口的权限。

## 验证层次

1. 可控测试：真实本地 D1、WechatBot 和会话 DO、受保护接口；模型、微信、汇率、时间和故障按用例控制。
2. 真实意图：读取已忽略、未跟踪且权限为 0600 的私密配置，用指定模型验证合成语句。没有账本或微信写操作。
3. 真实会话流程：生产构建、本地真实 D1／DO、真实模型及意图识别，微信网络传输使用可控替身；正常运行 WechatBot alarm 接纳、排队、处理、回复，不跳过微信确认校验。
4. 浏览器：生产构建下手机、PC 的完整现有用例，包括语言、主题、键盘焦点及跨端并发。

腾讯网络收发、客户端实际排版、云端故障恢复和持续运行成本与这些层次分别记录。已扫码连接不能代替业务断言；项目内测试输入也不声称来自腾讯。

## 本轮发现与修复

### 新建多笔草稿被误判为修改旧账

实际流程：确认入账合成咖啡后，再发送“整理成一份新的两笔支出草稿”，包含美元实际结算和人民币午餐。分类返回 `revise`，进入已入账草稿的修改提示，新草稿没有创建；原有账目没有新增或修改。

已用相同文本、咖啡上下文，通过共享 `wechatConfirmationIntent` 单独复现：新增 4 条回归中的第 91 条失败，实际 `revise`，预期 `other`。原规则将 `revise` 描述为任何修改要求，没有先明确操作目标，“整理新的草稿”因此与修改旧草稿混淆。

最小修复仅调整共享分类提示：先识别目标，明确新增独立收支／新建一份或多份草稿属于 `other`；修改针对已有展示草稿或账目。原身份、展示时间、版本、确认、幂等及金额检查均保留。修复后的 4 条真实模型回归通过。入口：

```sh
MONI_REAL_WECHAT_INTENT_SMOKE=1 pnpm exec tsx scripts/real-wechat-intent-smoke.ts 91 92 93 94
```

长流程继续发现，在仍有缺金额草稿时，币种筛选追问有一轮没有进入查询主模型；单独扩展后，“那按类别分一下，其他条件保持刚才的。”也曾被分类为草稿 `revise`。补充边界规则：统计的日期、币种、过滤和分组追问进入 `other`，由主助手使用权威查询历史处理；`unclear` 只用于批准意图及批准目标不清。新增的 6 条真实语句覆盖该边界，也保留“只确认美元那笔”属于非完整批准的验证，修复后 6 条通过。整体意图集扩展至 100 条。

### 手机取消恢复后焦点丢失

浏览器全量回归发现，备份恢复的 begin 响应丢失后取消，手机端焦点没有返回文件选择框。桌面通过，手机独立复测仍失败。探针确认恢复焦点时输入框仍为 `disabled`；页面稳定后直接聚焦可成功，排除了控件本身无法获得焦点。账本取消与解除恢复锁不受影响。

原 `requestAnimationFrame` 没有保证 React 已提交重新启用控件的状态。最小修复在 `RestorePreparation` 记录一次返回焦点请求，等 `busy=false`、恢复读取结束、预览已清除的已提交状态后聚焦。保留原有回归断言，不增加等待时间或在测试中代替产品聚焦。修复后手机与桌面的 6 项恢复激活测试全部通过。入口：

```sh
pnpm exec playwright test tests/e2e/restore-activation.spec.ts --workers=1
```

### 已保存结果被最后一次模型失败掩盖

本地故障注入稳定复现：`prepare_draft` 工具成功后让最后一次模型请求返回 502。人工确认模式下，完整草稿已经保存但没有正常展示；直接入账模式下，正式账目已经提交，却返回“没有自动入账”。2 项针对性用例在修复前均失败。原因是回复仅按模型 run 是否完成选择成功／失败文案，而财务工具事务可能早已提交。

最小修复复用原有 `prepare_draft` 业务回执，在同一财务事务内写入普通 run／thread 关联 ID，不增加表或密钥。微信回合失败时以这些回执找到本次草稿，再读取当前 D1 状态：待确认则完整展示，已入账则返回真实收据，已取消则显示取消并清理确认引用。即使工具结果的聊天记录写入失败，也可从业务回执核对已提交结果。旧回合缺少关联信息时仍可读已有工具结果；无法确认结果的通用失败文案不再断言“没有自动入账”。不重放模型或财务操作。

人工／直接入账分别覆盖末次模型故障和工具结果历史写入故障，另覆盖本人抢先取消后的故障，5 项用例均通过，并检查重投消息不增加模型调用。入口：

```sh
pnpm exec vitest run --config vitest.workers.config.ts tests/worker/wechat.test.ts -t 'shows the saved|cancels a saved draft'
```

### 摘要失败在同一回合重复等待

真实长流程中，摘要超时后虽正确回退，下一工具步骤仍会再次等待摘要。可控时钟复现同一中间件实例失败后发起了第 2 次摘要，新用例修复前失败。

每个会话运行独立创建中间件，现记录本回合摘要是否已失败：失败后该回合后续摘要请求立即回退，下一条消息的新运行仍可重新尝试。没有新增全局缓存，不修改官方检查点或完整历史，也不延长 15 秒预算。官方有效检查点仍可正常复用。

单元回归验证后续步骤立即继续、当前输入和 101 条历史保留、新运行重新尝试。真实本地微信 DO 对服务错误、空摘要、超长摘要分别断言整次记账运行只尝试一次失败摘要，仍能整理及确认账目，3 项通过。最新构建另用真实模型验证摘要指代、原始历史保留、DO 重启后复用和不重放，共 2 次摘要与 2 次问答全部通过。

### 测试断言与运行资源

- 状态疑问本身不得入账；后续明确同意可确认仍有效的完整展示，或先重新展示再等待同意。将真实流程用例改为核对这个财务效果，避免把所有非批准意图都误写成“必须重新展示”。
- 20 笔并不必然超过完整展示预算；已补正边界测试，验证完整可见的 20 笔可按同一版本入账，21 笔工具输入拒绝；另行保留真实超长展示不能确认的用例。
- 一次并行运行中的原有用例超过 5 秒；独立复测 415 ms 通过。最终复跑整套本地检查，不调大超时来掩盖失败。
- 临时诊断探针移除，不留原始模型错误、提示词、密钥或个人配置日志。
