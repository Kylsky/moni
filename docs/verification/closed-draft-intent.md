# 双入口：关闭草稿后的确认与长历史

2026-10-19，接续[并发草稿决策](concurrent-draft-decisions.md)。本轮继续检查普通会话和微信，修复可复现问题并回归相邻流程；没有增加功能或依赖。

## 确认的问题

已入账或已取消的草稿，经过一次查账或无关闲聊后，再回复“确认，记上吧”，两个入口可能跳过只读意图判断，直接进入主记账模型。旧逻辑把“没有待确认草稿／上一轮没有核对标记”等同于“不需要识别确认”。

受保护接口、真实本地 D1／DO、可控模型的 8 个组合均在修复前失败：两个入口 × 已入账／已取消 × 查账／闲聊。测试启用本人已有的直接入账权限，并让主模型尝试重放原消费，实际复现了合成账本中不应发生的写入。个人账本没有参与。

## 最小修复

- 普通会话和微信对有效新消息均执行已有的只读意图判断，不再以待确认数量或上一条消息标记决定是否跳过。
- 没有可确认目标时，明确确认只返回当前没有待确认草稿，不交给主模型重新整理旧消费。空会话同样处理。
- 识别确认和授予入账权仍是两件事：网页保留本人展示快照与程序核对状态，微信保留发送回执、创建时间和加密引用；最新版本、原子写入、执行撤销与业务去重继续由原命令检查。
- 真正的新消费仍进入主模型；已入账、已取消的旧草稿不会永久挡住后续正常记账。

两个入口删除提前跳过条件，以及普通会话因此不再使用的导入；网页的程序核对标记另按下述故障回归收紧。未改分类提示、金额、汇率、权限、存储结构或历史。旧版 API 未携带网页展示字段的兼容边界保持原样。

随后检查分类故障，两个入口又复现了相同的提示问题：首次描述消费、分类服务返回 401 时，旧文案声称“草稿已保留、直接再次确认”，但此时主模型从未调用，也没有草稿。新增两个回归先复现失败，再将同一中英文文案改为明确“本次消息尚未处理，已有草稿保持原样，稍后重试这条消息”。恢复服务后重新描述，只生成一份待确认草稿，没有正式入账。

继续沿失败分支检查，还确认了网页核对状态与微信的一处差异：查账或暂缓已撤销核对证明后，普通会话的分类失败回复错误设置 `moniDraftReview=true`，使下一句被识别为确认的“好的”得到重新授予的证明。两项普通会话回归在修复前失败，同场景的微信两项回归原本通过。现在只有实际重新展示草稿能新建核对状态；其他程序回复至多保留原本有效的证明，失败提示不能恢复已经撤销的证明。原本确实已展示的草稿遇到短暂故障后，明确重试确认仍可完成。

代价是先前跳过分类的新消息现在多一次只读模型调用，仍使用已有的 15 秒首次期限和仅针对暂时故障的一次 30 秒重试。分类失败不转交主记账模型；手动记账和普通筛选统计不受影响。

## 回归矩阵

| 场景 | 检查 |
| --- | --- |
| 空会话直接确认／全部确认 | 两个入口均不调用主记账模型，不产生草稿或账目 |
| 已入账／取消后查账，再确认 | 无额外正式写入，不重放旧消费 |
| 已入账／取消后多轮闲聊，再确认 | 插入 64 条合成历史，超过旧 32 条检查窗口；完整前缀保留，无额外正式写入 |
| 上述流程之后真正新增 9 元消费 | 已入账的 35 元保留，新总计 44 元；原来取消时仅产生新 9 元 |
| 448 种状态组合 | 两份草稿的四种状态、展示证明、新旧版本及七种意图；只有当前已展示且全部完整的新版本可进入确认 |
| 全部确认期间新增或补全草稿 | 重新展示；此前明确排除、仍缺信息的草稿继续排除 |
| 首次描述时分类失败，随后恢复 | 不声称已生成草稿、不调用主记账模型；后来重试正常生成一份草稿，不自动入账 |
| 查账／暂缓撤销核对，随后分类故障，再回复“好的” | 两个入口仍需重新展示，不能恢复旧证明；重新展示后明确同意可正常入账 |
| 既有长会话与摘要故障 | 36／40／1,100 条历史、DO 重启、摘要服务失败／空／超长，完整历史与后续确认均保留 |
| 手机／PC | 空会话确认后新增消费；已入账后查账、闲聊、重复确认、刷新恢复及已有并发场景 |
| 真实模型 | 两个脚本追加空会话确认、查账后重复确认、闲聊后重复确认；使用临时合成账本 |

本轮增加 18 项接口测试及 2 项单元测试，手机／PC 新增 2 项并加强原连续会话场景。既有浏览器模型夹具及默认本地测试运行时显式响应新增只读分类请求，默认只返回 `other`，不能替测试授予确认权。故障注入改以实际刷新阶段定位，不再依赖模型请求序号。
