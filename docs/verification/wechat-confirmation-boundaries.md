# 微信确认：故障记录与边界

2026-10-19。本次范围是已授权的微信确认、幂等和反馈准确性；不新增聊天撤销正式账目、跨草稿批量批准或自动合并连发消息。

## 本次真实故障

使用者在微信发送明确确认后，仍收到重新核对和澄清提示，正式账目未增加。真实模型请求均成功，D1 没有发生入账事务失败。

只读核对会话回执及加密投递记录，确认两个阶段：

1. 视觉预览补发直接调用 SDK，没有同步可执行确认引用。第一条确认已识别为 confirm，但接收时未携带有效的展示引用，程序正确要求重新核对。此为联调补发流程遗漏；可确认发送必须复用 `draftReply → deliver`，成功后持久化 shown 引用，不能将 SDK 的成功回执等同于程序已建立确认上下文。
2. 重新展示后，后续确认引用、版本和会话均正确，但分类模型把普通明确同意误判为 unclear。用合成草稿复现：reviewed=true 且存在一份其他旧草稿时，“确认／确认啊”三次均误判；只把其他草稿数改为 0，三次均通过。

修复将“已明确绑定的当前草稿”和“其他待处理草稿数量”在分类提示中分开说明。旧草稿存在本身不构成歧义，普通同意只指向展示的整份草稿；部分同意、修改、条件、否定、其他目标及跨草稿批准仍不直接入账。模型继续仅返回意图，程序保留展示、来源、版本及幂等检查。

## 边界审计发现并修复的缺口

- **目标缺失时误选其他草稿**：原选择表达式会在已绑定目标不存在时回退到唯一旧草稿。合成测试确实产生错误入账。改为只在完全没有绑定引用时寻找唯一候选；有引用时只认其 ID，并显式核对 candidate.id。
- **已入账后否定／修改的错误反馈**：原逻辑可能回复“暂不入账”，或把修改请求交给生成草稿流程。现对当前已绑定且已入账的目标，明确说明真实状态，指引在网页修改或撤销，不创建替代账目或声称撤销成功。
- **网页先确认成功的并发回执**：原微信事务冲突后，只处理仍待确认的状态，会把已入账误报为没有唯一目标。现重新读取结果后明确返回已入账，不再次写账。

上述三个缺口共四项失败测试，修复前全部复现；修复后转绿。没有在个人账本上重放确认或修补业务数据。

## 已覆盖的行为

下表汇总本次核对的处理规则。相关关键路径使用真实本地 D1/DO 和受控模型、微信及汇率替身做集成验证；语义判断另有真实模型合成用例，不能混作手机端验收。

| 情况 | 处理 |
| --- | --- |
| 当前草稿有效，另有旧草稿 | 自然同意只确认当前展示的整份草稿。 |
| “确认啊／好嘞／OK／不用改了直接记上” | 真实模型按当前核对上下文理解；不要求固定指令。 |
| “这份全部入账，其他草稿先别记” | 只批准展示的整份草稿，其他草稿保持未入账。 |
| 修改与同意混在一句 | 先修改并重新核对，不按旧内容入账。 |
| 否定、疑问、引用、条件或未来承诺 | 不当作当前入账许可。 |
| 部分项目、其他草稿、跨草稿全部批准 | 澄清目标，不扩大当前执行范围。 |
| 描述与确认同批到达、完整草稿尚未展示 | 重新展示后等待新的明确同意。 |
| 同批两个明确确认、重复消息、重复同意 | 幂等处理，只形成一次正式入账。 |
| 网页在意图判断期间修改草稿 | 原版本不能入账，重新展示最新内容。 |
| 网页在意图判断期间抢先确认 | 返回真实已入账状态，不重复写入。 |
| 已入账后再要求先别记或修改 | 说明已经入账，并指引网页处理，不声称撤回或生成替代账目。 |
| 展示目标缺失、取消、会话失效 | 不把确认转移给其他草稿。 |
| 确认已提交，但微信回执发送失败或 DO 重启 | 复用同一投递 ID 与保存回执，不重跑分类或再次入账。 |
| 未展示成功、信息不完整或完整回复过长 | 不建立可直接确认的完整草稿许可。 |
| 查询、其他话题、修改或暂不入账之后 | 原核对上下文按规则失效，不把之后的普通应答误用于旧账。 |
| 模型超时、故障或非法输出 | 不入账；允许后续本人新消息再次尝试。 |
| 非本人、群消息、断开、换会话或备份恢复 | 不继承旧渠道确认权，迟到结果不能写账。 |
