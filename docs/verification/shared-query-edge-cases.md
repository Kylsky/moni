# 普通会话与微信：多组统计边缘情况

后续并发状态补查见[双入口：并发入账时的暂缓与修改](concurrent-draft-decisions.md)。本文保留当轮结果。

2026-10-19，接续[双入口通用逻辑补查](conversation-parity-followup.md)。本轮按要求继续检查两种会话，直接修复确定的问题并补回归；没有扩大功能范围。

## 确认的问题

1. 同一轮先查询支出、再查询收入，随后直接入账一笔午餐，旧共享工具只刷新最后一次查询。真实本地 D1／会话 DO 的受保护接口回归在修复前失败：支出卡仍为 0，实际已入账 35 元，最后一张收入卡刷新成功。
2. 微信同一轮存在多个查询结果时，格式化回复只采用最后一组。以合成支出 35 元、收入 1,200 元复现：旧回复只包含收入，遗漏支出；回归在修复前失败。

## 修复边界

- 共享工具按查询标识保留本轮各组结果。直接入账后逐组重新查询 D1，成功替换对应卡片；某一组失败只把该组标为不可用，保留真实财务回执，不能因统计失败重新入账或展示那组旧金额。
- 普通会话即时展示及刷新后的历史使用同一套多结果解析。微信也按标识合并刷新结果，逐组输出 Markdown；多组内容超过单条容量时明确提示到网页查看，不静默遗漏最后或前面几组，也不截断核对内容。
- 更新早先某张统计卡不会改变“上一查询”的指向。后续追问仍沿用最后一次实际查询的条件；即使最后一组刷新失败，也不会错误切回前一组筛选。
- 兼容已有历史中的单结果和刷新失败表示；新结果校验标识、结构和最多 12 组的执行边界。合并刷新的统计数据有容量保护；不适合放入本次回复的组明确不可用，已入账交易不受影响。
- 金额、固定折算、确认权限、草稿版本、会话隔离、执行撤销和去重继续使用既有共享逻辑。未添加依赖或修改私密配置。

## 回归覆盖

| 场景 | 入口／验证方式 |
| --- | --- |
| 两组查询后直接入账，前后两组均刷新 | 受保护普通接口、手机／PC 浏览器 |
| 第一组或最后一组刷新故障，其他组与财务结果仍正确 | 真实本地 D1／DO 故障注入 |
| 部分刷新故障后的最后查询条件不漂移 | 持久化原始工具历史与共享筛选恢复 |
| 原查询之后记录增加，刷新后的多个大报表超过合并容量 | 真实本地 D1／DO、只保存一次正式入账 |
| 微信只查统计、人工草稿＋多组统计、直接入账＋多组统计 | 真实本地 D1／DO、模型与微信替身 |
| 多组微信回复过长时的明确提示 | 真实本地 D1／DO、18 个合成类别 |
| 旧历史、多组成功／失败、错配标识、损坏结构、数量越界 | 单元测试 |

容量测试中的大报表最初放在模型原查询之前，触发了已有上下文容量限制，无法到达新增刷新分支；最终改成在原查询和正式入账之间插入合法合成记录，验证并发增长后刷新变大的实际边界。没有为迁就测试提高生产上下文或存储限制。
