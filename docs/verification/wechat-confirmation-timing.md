# 微信提前确认与会话上限故障

2026-10-19。本次仅修复确认时间边界及会话上限反馈，不调整记忆策略、上限、入账权限或已有业务数据。

## 已确认的故障与原因

使用者确认：自然语言同意是在草稿展示前发出的。旧实现只保存消息被接纳时的草稿引用；消息在草稿展示后才被轮询收取时，会错误继承新引用，造成提前入账。先前“描述和确认同批到达”的测试不能覆盖这个时间差。

回归在受保护接口、真实本地 D1/DO 与受控微信／模型的边界复现：描述已接纳，模型响应暂挂，提前创建同意消息；释放模型并展示完整草稿后，再通过下一次轮询收取那条同意。旧实现预期 0 笔、实际写入 1 笔。只改变确认的创建时间即可区分有效和无效授权，排除单纯分类失败或重复投递的解释。

另一个真实失败由日志确认是 `context_limit`：工具循环达到既有上下文上限。运行错误与微信回复原来统一映射为 AI 服务故障，无法告诉使用者正确的下一步。接纳前的 `history_limit` 也被同样误报。

## 最小修复

- 接纳并验证 SDK 协议中的 `create_time_ms`，与消息一起加密保存。草稿发送成功后保存 `shownAt`；收取时的引用仍需匹配，消息创建时间还须严格位于展示成功之后、消息接纳之前或当时。
- 时间缺失、非法、未来、相同毫秒以及缺少新时间字段的旧引用均不能直接批准；重新展示，等待新的自然确认。保留单份、批量、版本、身份、数据集及 D1 事务幂等检查。发送失败重试、重启不会使旧消息获得新授权。
- 展示时间采用发送成功回执之后的本机时间，属于保守边界：上游已展示但回执尚未返回期间发出的确认可能需要再次核对。依赖微信创建时间和运行环境时钟，不能把协议时间称为用户已读证明；异常或缺失时间可通过网页核对入账。
- 持久化只放行固定的 `context_limit` 错误码，其余服务错误继续脱敏。网页显示上限原因，不提供必然再次触及上限的重试；微信区分接纳前拒绝与回合内失败，并提示先检查已保存的草稿和账目，再新建微信会话。
- 工具已保存的草稿保持原样并附待确认提醒；不将部分执行误报为“什么都没保存”，不重放旧确认，不删除真实记录。

## 回归入口与结果

`pnpm test:workers tests/worker/wechat.test.ts`：82 项通过，包含本次新增的 9 项：延后收取的提前单份／批量确认、缺失／非法／未来／同毫秒／旧引用与重启、接纳前及工具执行中达到上下文上限。提前确认和两个上限场景均先失败，修复后转绿；新的合法确认仍可入账。

原有自然确认、批量确认、并发修改、重复入账防护、回执重试与权限检查继续覆盖。测试中的人类后续回复跨过展示的同一毫秒；同毫秒拒绝另有明确反例，不放宽生产时间条件。

全量 `pnpm check` 通过：170 个文件的格式检查、518 个中英翻译键、21 项单元测试、259 项 Worker 集成测试和类型检查，另有 1 项原有跳过。`pnpm build` 与 `pnpm check:private` 通过。中途类型检查发现手动构造错误事件需使用 SDK 的 `EventType.RUN_ERROR`，修正后重新完成全量检查与构建。

新构建已恢复本机私密持久化联调服务，连接状态为 connected、权限为 review；只读核对确认会话未切换、账目数量未变化，原误入账记录仍保留。未重放个人确认、补写消费或擅自删改账目。手机端重新确认及真实时间字段的端到端验收仍须实际测试，不把替身测试计为实机成功。未提交、推送或云端部署。

使用者随后提出持续微信会话和滑动窗口／auto compact 的方向，另行调研 TanStack AI 官方能力。本次错误提示按当前仍生效的硬上限如实反馈；这不代表已经接入自动压缩，或将强制新建作为后续长期方案。
