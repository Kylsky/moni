# 双入口：并发入账时的暂缓与修改

后续关闭草稿和跨话题补查见[关闭草稿后的确认](closed-draft-intent.md)。本文保留当轮验证结果。

2026-10-19，接续[多组统计补查](shared-query-edge-cases.md)。本轮继续核对普通会话与微信的并发操作、草稿状态和后续确认，没有扩大功能范围。

## 可复现的问题

本人在会话里要求“先别入账”或修改草稿，分类服务尚在识别；此时另一端已经确认其中一份草稿。旧逻辑可能仍回复“暂不入账，草稿会保留”，或者把修改请求继续交给主模型。

- 微信只在“全部确认／查看待确认”识别后重新读取草稿，暂缓与修改仍使用识别前的状态。
- 共享草稿决策只在目标**全部**已入账时拦截暂缓／修改，遗漏“部分已入账、部分仍为草稿”。普通会话虽然已刷新状态，仍受第二个问题影响。

测试在真实本地 D1／DO 和受保护接口上，用可控分类闸门制造准确时序。8 个场景覆盖两个入口、暂缓／修改、单份／两份目标；修复前有 6 项失败，普通会话的单份已入账两个场景原本正确。正式账目的原有写入保护未被突破，本轮复现的是误导回复和不应进入主模型的修改分支，没有对个人账本制造错误交易。

## 最小修复

1. 微信所有已识别意图在决策前重新读取当前草稿，与普通会话保持一致。
2. 共享决策发现所选目标中已有入账记录时，暂缓或修改直接说明现状，不把整个旧批次继续交给记账模型。其余未入账草稿不会被修改或自动补入。
3. 中英文回复兼容单份与混合状态批次，明确“已有入账记录，本次未改动；未入账草稿仍保留”，并指向已有账目编辑入口。
4. 微信告知部分已入账后，移除旧混合批次引用，使后续只改剩余草稿的请求可正常执行；没有剩余草稿时保留已入账上下文，继续阻止重复确认进入主模型。
5. 普通会话中，程序回复的 `moniDraftReview=false` 只表示原确认授权已撤销，不表示可以跳过后续只读意图判断。旧代码把两者混为一谈，导致提示已入账之后、无待确认卡时再次回复“确认”进入主模型；两个单份回归在修复前再次复现失败。现在任何程序核对回复均保留只读分类上下文，只有原本为 `true` 的核对状态才能配合本人展示证明授予确认权。

未修改分类提示、模型、两档权限、金额规则、正式入账命令、幂等或版本检查；没有新增依赖。

## 回归范围

- 普通会话新增 4 项、微信新增 5 项受保护接口／D1／DO 回归，验证分类进行中由另一端完成入账后的最新决策，以及微信剩余草稿的正常修改和确认。
- 两份目标的场景继续测试：第一次确认剩余记录只重新展示，第二次明确确认才入账；普通会话保留原 35＋9＝44，微信保留原 35＋12＝47，不采用之前请求修改的 20，也不重复入账。
- 对旧批次的暂缓／修改，两个入口都断言不会继续调用主记账模型；微信同批其他草稿状态保留。之后明确只修改剩余草稿时，主模型仍可正常更新那份草稿。
- 单份已经入账的暂缓／修改回复之后，两个入口继续确认均不新增交易；普通会话无展示引用时也明确没有待确认草稿。
- 新增手机、PC 浏览器场景，模拟已展示旧批次的请求与另一端确认交错，检查提示、已入账卡、剩余草稿复核及刷新后恢复。
