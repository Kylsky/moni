# Moni 微信入口与专用会话设计

日期：2026-10-18；2026-10-19 更新。状态：使用者已另行授权接入，现已提供本地实现与测试，真实账号扫码、收发及云端持续运行仍待验收。作为可选扩展，不改动现有 v0.1 的 19 项验收基线。当前实现与使用说明见[微信接入说明](wechat-integration.md)。

核心决定：**同一本账本，多一个微信 ClawBot 入口；微信默认对应一条独立的专用会话。**

依据：[产品需求](../PRODUCT.md)、[术语表](../GLOSSARY.md)、[技术方案](technical-design.md)及[ClawBot 可行性核查](research/2026-10-18-wechat-entry-feasibility.md)。初次设计记录仅授权文档；2026-10-19 使用者明确要求接入，并要求复用 GitHub 现成库，授权了本次实现。真实云资源、提交推送和部署仍遵循原有单独批准门槛。

## 已确认的产品关系

- 账本共用：微信产生的正式账目在网页可见，网页修改账目后，微信再次查账基于最新记录重新计算。
- 会话独立：微信连续提问沿用微信会话的上下文，不混入网页其他会话；微信专用会话不是第二本账本，也不是第二个使用者。
- 逻辑共用：文字理解、分类、标签、汇率、草稿、查询和统计复用 Moni 的能力，AI 层仍采用 TanStack AI 与已选模型配置。
- 历史可见：网页会话列表可展示标记为“微信”的会话，查看消息、查询结果和记账草稿；会话历史仍纳入完整业务备份。
- 主动记账与查账：微信只增加收发文字的入口，不因此加入支付账单导入、语音识别、图片识别或主动提醒。
- 确认原则不变：AI 先生成草稿，由本人明确确认后正式入账；未确认草稿不计入统计，重复投递或重复确认不能重复入账。

例如，微信中先问“最近三个月外卖花了多少钱”，再问“那上个月呢”，第二问沿用外卖条件；网页另开的普通会话不自动带入这些条件。之后在网页修改相关账目，微信再次提问时重新查询当前账本。

## 技术映射与数据边界

消息入口、身份和会话分别建模：Bot 账号标识用于接收消息，已绑定的微信发送者标识用于核验本人，Moni 会话标识用于保存交流上下文。微信消息提供的身份不能直接充当网页 Access 身份，也不能由第一个发消息的人认领账本。

接入时复用当前 Worker + D1 + 会话 DO 架构：D1 保存消息入口标记、专用会话及业务历史；现有会话 DO 执行对应 AI 回合。Bot 账号级接收、游标与退避由消息适配层负责，不能让各会话分别竞争接收同一个 Bot 的消息。

可行性核查中的“Bot 接收 DO → 会话 DO”是技术候选方案；接收层的具体实现、绑定、连续轮询恢复及成本仍待验证。当前不选定社区 SDK，不引入整套 OpenClaw，也不因此承诺新增常驻服务器或长期在线能力。

所有写入复用账本校验、活动数据集范围、草稿版本和操作幂等。微信消息需有可持久核对的接纳标识，重复接收不能再次创建同一草稿或重复启动同一回合；已处理但回复结果不确定时，也不能重新执行业务操作。

Bot token、回复所需的敏感上下文和授权状态不进入公开仓库、前端构建、日志或业务 JSON 备份。备份保留会话及必要的来源信息，但恢复不自动恢复微信授权、旧确认执行权或未完成的发送任务。未启用或断开微信入口时，网页记账和查账仍可使用。

网页可查看微信会话，不代表所有网页消息都要转发微信。回复默认返回本轮请求的入口；是否允许在网页继续微信会话，以及是否同步发送到微信，留待具体交互设计。

## 本次实现采用的交互

- 在通过 Access 验证的设置页发起扫码，只绑定官方确认响应中的扫码用户，不接受首个消息发送者认领。
- 使用 `wechat-ilink-client` 的底层客户端；账号级 `WechatBot` DO 负责游标、加密凭据、可靠接纳及重试，会话 DO 继续执行现有 TanStack AI 能力。
- 采用两档记账权限，默认人工确认；微信展示完整草稿，由本人自然回复明确同意后入账，不要求指令或确认码，网页仍可编辑和确认。本人可在设置中开启直接入账。常规回复不附固定网页链接。详情见[记账权限](posting-permissions.md)。
- 网页可查看微信历史、编辑和确认草稿，新消息从微信发送，不将网页内容自动转发微信。
- 在设置页可明确新建微信会话，保留旧历史；删除会话后暂停接收，待本人新建后继续。断开连接立即撤销渠道执行权并保留账目和历史。
- Token、回复上下文及登录状态使用部署专有 Secret 加密，存于 DO；D1 仅保存无凭据的执行约束。业务恢复保留会话来源，旧授权和发送队列不恢复。

## 仍待真实验证的细节

- 本人账号的 ClawBot 可用性、实际扫码、验证码、重新授权和撤销后的真实行为。
- 微信侧实际回复长度、context token 有效期、网络失败和重复发送的服务端表现。
- Cloudflare 上的连续长轮询、部署重启恢复、网络可达性、延迟及实际费用。
- 真实模型与微信组合的端到端记账、连续查账、微信确认和直接入账验收。

上列原候选问题中，绑定、会话管理、确认入口和回复形式已按本次实现确定；账号可用性、实际回复限制、网络可达性及连续运行费用仍待真实验证，不以本地替身结果代替。

## 后续验证场景

以下仅用于微信入口排期后的设计与验证，不替换 v0.1 验收表，也不表示已经运行：

1. 微信文字形成独立会话，网页能查看其历史，其他会话不自动继承上下文。
2. 连续查账可沿用条件；网页修改账目后，微信重查结果随之更新。
3. 微信生成的草稿在本人确认前不入统计，确认后与网页共用同一正式账目。
4. 重复消息、失败重试和重复确认不重复生成业务操作；回复失败与入账失败可以区分。
5. 非绑定发送者和已撤销的绑定不能访问账本；失效授权不会降低网页 Access 检查。
6. 导出恢复保留微信会话历史，排除敏感凭据，旧投递、旧确认和未完成发送不自动重放。
7. 微信入口未启用或暂时不可用时，原有网页功能仍可独立使用。
