# 微信 ClawBot 接入

2026-10-19。使用者另行批准的可选扩展，沿用同一本账本、微信专用会话及人工确认原则；不重新定义 v0.1 的原验收清单。

## 依赖选择

采用 [photon-hq/wechat-ilink-client](https://github.com/photon-hq/wechat-ilink-client) 的 npm `wechat-ilink-client@0.1.0`、`ApiClient`。扫码、状态轮询、收消息、发消息都通过该客户端调用，不使用它的常驻内存 monitor。`qrcode-generator@2.0.4` 仅在网页显示二维码，不将授权信息交给外部二维码服务。

也核对了使用者提供的 [wong2/weixin-agent-sdk](https://github.com/wong2/weixin-agent-sdk)：当前 `0.5.0` 的公开接口是 `login/start/Bot`，账号和游标写本地文件，接收为常驻 Node 循环；没有可替换为 DO 存储的公开接口。直接使用会增加独立 Node 服务或需要改造其存储层。因此本次选有独立底层客户端的前者，继续使用 Cloudflare。

腾讯协议依据为 [Tencent/openclaw-weixin 的官方协议](https://github.com/Tencent/openclaw-weixin/blob/874637a0dbc24050f72d1385add4fc6170a2d726/docs/protocol_zh_CN.md)，当前核对提交仍为 `874637a0dbc24050f72d1385add4fc6170a2d726`。SDK 是社区项目，不能据此声称获得腾讯官方支持。

依赖补丁 `patches/wechat-ilink-client@0.1.0.patch` 仅增加可注入的 fetch，随 pnpm 锁文件重现安装，不直接修改未记录的 node_modules。Moni 的传输适配补上 SDK 0.1.0 与当前协议的差异：POST 获取二维码、应用版本头、验证码、独立验证 HTTP 和业务返回码、无损 uint64 消息 ID、限制响应大小、限制到腾讯 HTTPS 主机并拒绝 HTTP 跳转、脱敏错误、完整读取后清理超时计时器。升级 SDK 时重新验证这些行为；不引用 SDK README 推测的 context token 固定有效期。

## 使用方式

1. 完成账本及 Cloudflare Access 配置。微信管理接口与全站一样仅对本人开放，无匿名 webhook，也不把微信身份当成 Access 身份。
2. 本地执行 `pnpm wechat:setup`。脚本先确认 `.dev.vars` 被忽略且未被跟踪，生成部署私有的 64 位十六进制 `WECHAT_SECRET`，保留其他配置，设为 `0600`，不会显示密钥。再次执行不改动已存在的有效值。
3. 云端由部署脚本自动生成独立的 Cloudflare Secret `WECHAT_SECRET`；本人无需填写。重复部署仅补缺失密钥，不能覆盖已有值；预览环境独立生成。不要写入 wrangler vars、GitHub Issue、前端或业务备份。
4. 执行 D1 迁移与 Worker 部署，包含 D1 `0017`、DO `v2` 和 `WECHAT` 绑定，预览与生产互不引用对方 DO/D1。
5. 本人打开“设置 → 微信入口 → 连接微信”，使用自己的 ClawBot 微信扫码并在手机确认；按需输入手机验证码。网页只接收展示二维码、连接状态和普通会话 ID，Bot token 不返回浏览器。
6. 如需自然语言功能，在网页“设置 → AI 助手”保存模型配置；可在配置 AI 前先扫码绑定，消息会明确提示配置 AI。微信可发送“午餐在肯德基吃了 35”或“最近三个月外卖花了多少钱”，后续问题沿用微信会话上下文。默认回复完整草稿，核对后自然回复“确认”“记上吧”等明确同意即可入账，或登录网页核对编辑。不要求固定指令或确认码；否定、疑问、修改要求和不明确的同意不直接入账；常规回复不附固定网页链接。本人可在设置中选择“直接入账”。详见[记账权限](posting-permissions.md)。

网页中的微信会话只接收历史刷新、草稿编辑和确认；新问题在微信发送。在设置页可明确新建微信会话清空上下文，旧历史保留；断开后新微信消息无法访问账本。

## 草稿回复排版

ClawBot 的官方插件支持部分 Markdown；依据与版本边界见[官方源码核查](research/2026-10-19-wechat-message-format.md)。Moni 使用加粗、空行和列表：状态、消费标题、原币金额、日期、类目、可选标签与备注分别展示，多笔逐项编号，主币种合计单独加粗。外币保留固定折算金额、汇率来源与依据日期；本人提供实际结算时只说明实际结算，不编造汇率。

金额由现有账务逻辑格式化，去掉重复的 `CNY ¥` 等前缀；不额外调用模型。自由输入中的 Markdown 被转义，备注原文仍保留在草稿、账目及备份中。完整回复过长时继续要求网页核对，不截断内容后允许微信确认。普通回复不增加固定网页链接或指令码。手机客户端的实际显示需要实机核对。

需要建立可确认上下文的草稿发送，必须经现有 `draftReply → deliver` 路径，在微信发送成功后保存对应 ID、版本和 shown 引用。联调直接调用 SDK 的纯视觉补发不建立该引用，不能据此承诺下一句即可入账；缺少引用时由系统重新展示核对，不能绕过校验。微信侧显示与程序侧确认引用需要分别核对。

## 待入账提醒与批量确认

普通会话与微信现已共用只读意图识别、草稿决策和正式确认命令；手机／PC 网页支持已展示草稿的自然确认及批量确认。微信专用层保留绑定、收发、消息时间和重试检查；共享行为与最新验证见[双入口会话行为](verification/shared-conversation-intent.md)。

后续补查已同步普通会话的财务回执恢复、防止财务已提交后的模型重放、空展示范围重复同意，以及批量数量、疑似重复与缺信息排除提示，见[通用逻辑补查](verification/conversation-parity-followup.md)。

2026-10-19 使用者追加授权：回复时提醒当前微信会话内尚未入账的草稿，支持一次核对多份草稿并明确确认。不增加定时催促；本人刚表示暂不入账时不立即再追问。新草稿、查账或入账回执仍有其他待确认内容时，由程序读取当前草稿状态，补充草稿份数、账目笔数及“不计统计”的说明，不能依赖模型正文中的提醒。已完整展示的草稿不重复附相同提醒。

“一起核对”“还有哪些没入账”只展示草稿；“全部确认”“把没入账的都记上”由独立 TanStack AI 分类为批量入账意图。未核对全部目标时，先展示本会话中完整草稿的逐笔明细、备注、日期、类目、原币及固定折算结果，等待下一条自然确认；不要求确认码或固定命令。普通“确认”仍只作用于最近完整展示的一份或一批草稿，不扩大到其他草稿或会话。

分类先判断操作对象：新增独立收支、整理一份或多份新的草稿进入正常记账流程；“修改”针对已有展示草稿或账目，不因出现“草稿”“整理”“备注”等词而拦截新的消费。真实模型与故障回归见[完整场景记录](verification/wechat-scenarios.md)。

批量引用绑定每份草稿的 ID 和版本，在发送成功后才标为可确认，并记录展示时间；消息接纳时保存当时的引用及微信协议 `create_time_ms`。确认消息的创建时间必须晚于展示成功时间，且不能晚于接纳时间；不能只按消息被收取的先后判断。提前发出、延后才被收取的同意也不能批准后来才展示的内容。时间缺失、非法、相同或旧引用没有展示时间时，重新核对后等待新的明确确认。批量正式入账与确认回执共用一个 D1 事务，沿用单份确认的金额、折算、身份、活动数据集、恢复锁、会话状态与幂等保护。任意写入失败则整批回滚；网页抢先入账、修改、取消或目标缺失时重新展示剩余可核对内容，不把旧确认移到其他草稿。明确“全部”时，还在事务内拒绝存在本批之外的新待确认草稿，重新核对后再继续。

信息不全的草稿明确排除并保留提醒；本人回复“全部确认”可确认已完整列出的部分，不因已告知排除的草稿反复要求核对。该排除仅在其仍缺信息时有效，补全后必须重新展示。超过一条消息的完整展示预算或 20 笔账目时要求网页核对，不截断后开放批量确认。同日、同币种、同金额的批内账目提示可能重复，由本人决定，不自动合并、删除或跳过。旧版单份引用的目标仍可读取，缺少展示时间则先重新核对。回归与真实模型合成验证见[验证记录](verification/wechat-pending-batch.md)；延迟收取的提前确认见[故障记录](verification/wechat-confirmation-timing.md)。

2026-10-19 追加确认后，微信持续使用同一个会话：官方 `@tanstack/ai-compaction` 自动将较早内容摘要化，保留近期完整回合，只缩减模型上下文；D1 的完整历史继续保存，网页按页回看。移除每会话 40 条上下文和 1,000 条／1 MiB 历史的固定门槛，保留单条及本轮安全预算。摘要故障保留原历史及最后有效检查点，安全回退到近期窗口；不换会话、不重放旧输入、不因摘要写正式账目。过大的当前请求可能已保存草稿，仍提示核对并附待确认提醒。详见[长会话验证](verification/chat-compaction.md)。

## 统计回复与图表

微信查询结果采用 Markdown 摘要：突出收入或净支出，分别展示支出、退款、匹配笔数、日期、时区与主币种；外币原币汇总另列。按类目、标签和时间趋势查询时展示相应分组，标签提示重叠口径。金额直接取可信查询结果，由程序排版，不额外请求模型。

分组按完整条目展示，最多 12 项并受回复长度预算约束；长趋势优先保留最近有记录的时段，再按时间顺序展示。省略明细时明确标注，不能当作完整分布；不裁掉总额、退款、筛选条件或统计口径。条件本身过长时明确指引网页核对；空结果不表述为没有实际消费。普通统计不附固定网页链接。

图片图表在官方协议上可行，无需公网图表 URL，但 Moni 当前尚未接入生成与媒体上传。Markdown 摘要和图片将是独立相邻消息，不能用 `![图片](url)` 代替。建议后续采用按需图表：类目条形图、时间趋势图；服务端根据同一查询结果生成 PNG，经腾讯加密上传，图片失败时保留文字。详见[图片能力调研](research/2026-10-19-wechat-statistics-media.md)。

## 恢复与失败语义

- 确认识别是只读回合：首次请求及完整回合最多 15 秒，临时服务／网络／流故障只重试一次，第二次最多 30 秒，总等待约 45 秒；关闭 HTTP 客户端内部重试，避免次数叠加。明确的客户端错误、无效输出和正常的不明确意图不重试。仍未取得有效结果时不入账，保留草稿并说明服务未完成；不要求重新描述消费。识别成功仍使用原草稿引用、版本与 D1 入账检查。仅记录失败原因类别、次数、耗时，不记录原始服务错误、正文或密钥。见[复现与验证](verification/wechat-confirmation-service-retry.md)。
- 一个部署仅启用一个 Bot、绑定扫码本人。DO 每次运行处理一个有界轮询批次或一个待处理投递，持久 alarm 续调，无常驻 Node 服务。长轮询使用 DO 会产生相应运行费用，线上延迟、恢复和成本需真实验证。[Cloudflare Alarms](https://developers.cloudflare.com/durable-objects/api/alarms/)
- 接纳消息与推进游标在同一 DO 存储事务中完成。按绑定、Bot、发送者及精确消息 ID 派生运行 ID；已接纳的回合不会因回复失败重新执行模型或草稿操作。
- SDK 的高层 monitor 不参与接纳顺序。待处理消息、回复上下文和凭据在 DO 中加密；去重标识、游标和状态同样只在部署状态中，全部排除业务导出。
- 同一回复内容用同一个 client_id 最多重试三次。发送草稿前核对当前版本、取消状态与原排除的缺信息草稿；目标变化时刷新明细并换新的传输标识，重新完整展示后才可确认。新内容重新计算三次预算，整条消息仍受原一小时有效期约束。上游成功但确认丢失时，不能承诺微信展示严格一次；可能重复显示回复，但不会重复执行记账模型回合或入账。超过重试或等待一小时后不重放，网页历史仍可核对。存储故障、重试期间修改及权限切换见[发送边界验证](verification/wechat-delivery-boundaries.md)。
- 财务工具成功后，最后一次模型请求或聊天记录写入仍可能失败。`prepare_draft` 在原财务事务的业务回执中记录 run／thread 关联；微信失败回复先据此读取当前草稿状态，保留真实待确认明细、入账收据或取消状态，不把模型失败当作财务未发生，也不为补发而重新执行。关联 ID 不是凭据，确认权限仍依原身份、展示时间、版本和事务检查。无法确认结果时提示核对已保存记录，不断言未入账。
- 同一回合同时记账与查账时共同展示草稿／收据和可信统计；在回复前按已验证的原查询条件重读当前正式账目，避免查询先于入账时返回旧合计。统计刷新失败时保留真实财务结果、明确统计失败，不用旧数字冒充当前值。多份草稿及失败后的恢复均核对全部业务结果。沿用批量完整展示、缺信息排除与长度保护，超长内容转网页核对，不截断后允许批准。新增组合验证见[补查记录](verification/wechat-missing-combinations.md)和[发送边界验证](verification/wechat-delivery-boundaries.md)。
- 授权 `-14` 要求重新扫码。断开会持久撤销 D1 渠道执行约束，阻止迟到 AI/草稿结果。轮询故障退避后恢复，网页不受影响。密钥变更后需重新连接。
- 业务 JSON 保留微信会话来源、历史、备注、草稿和查询结果，兼容未含 source 字段的旧 v1 备份；恢复后不恢复微信授权、旧确认权或发送队列。原绑定不能跨活动数据集继续执行。
- 删除会话不会由旧消息复活。本人新建微信会话后，旧会话待处理消息被丢弃，新消息进入新会话。绑定身份、权限、token 和 context 均不作为会话消息传给 AI。

## 验证入口与边界

- `pnpm check`：包括真实本地 D1、DO 与受保护接口，模型和微信均为可控替身。
- `pnpm build && pnpm exec playwright test tests/e2e/wechat.spec.ts`：手机、PC 的设置、扫码/验证码、草稿核对、明确入账、新会话、断开、中英文、主题与横向溢出。
- `MONI_REAL_WECHAT_SMOKE=1 node scripts/real-wechat-smoke.mjs`：只对真实官方二维码端点请求挑战，经过构建 Worker 与 SDK，不记录二维码内容、不扫码、不发送消息、不读取个人模型配置。未设置开关时跳过。
- `MONI_REAL_WECHAT_INTENT_SMOKE=1 pnpm exec tsx scripts/real-wechat-intent-smoke.ts`：私密配置中的同一模型验证合成确认语句，覆盖其他旧草稿存在时的自然同意、跨草稿批准、修改、否定及提示注入；不读写账本、不调用微信。未启用时跳过。
- `MONI_REAL_WECHAT_CONVERSATION_SMOKE=1 node scripts/real-wechat-conversation-smoke.mjs`：日常真实模型回归直接调用项目内微信处理流程，微信收发为可控替身；用真实本地 WechatBot／会话 DO 和 D1 验证连续记账、备注、草稿提醒、批量核对、自然确认、防重及连续查账。合成绑定与账目在独立临时存储中，结束销毁；不操作用户电脑微信、不改个人账本。最新结果见[长会话与微信自动联调](verification/chat-compaction.md)。
- 项目内自动回归与腾讯网络收发分开记录；本人扫码授权、客户端实际展示、云端长时间收取、Cloudflare 部署更新后恢复及费用需要各自证据。二维码接口成功不代表其他验收通过。此前手动收发证据见下方接入记录；日常业务回归无需反复人工发送。

实际执行结果记录在[微信接入验证记录](verification/wechat-integration.md)。
